# Find your place — React frontend

React + Vite implementation of the `codex/prototype-home` visual flow, using the live Hono/PostGIS API. Original `src/home-prototype` files remain intact. The green palette, fonts and household profile flow are retained. The dashboard centres the selected place, an area review, local KPIs, a combined service map, detailed records and a monthly cost calculator. Fictional scores, homes and service points are replaced with source evidence and explicit unknown states.

```sh
cd src/frontend
bun install --frozen-lockfile
bun run dev
```

Open `http://127.0.0.1:5173`. The Vite `/api` proxy targets the native macOS Hono container at `http://127.0.0.1:3080`. No frontend CORS exception is needed for local development. `bun run build`, `bun run typecheck` and `bun run test` validate this separate package; root package scripts can delegate to it.

The established question-by-question onboarding asks for anywhere/specific scope, each household member and age, bedrooms, tenure, housing budget and transport. Explicitly saved household defaults remain in this browser. Choose any number of required/preferred service criteria; anywhere scope lists all recorded towns and cities before opening the location dashboard. Results use `/places`, `/place-anchor`, `/criteria`, `/layers`, `/assess` and `/features`. Change the place directly from the dashboard without repeating setup. Sidebar criterion and radius changes are drafts until applied; the review clearly flags pending changes and keeps the applied results together. Request versions prevent outdated responses from replacing a newer review. The town anchor uses the backend's point-on-surface when available; its fallback is visibly labelled as a source-town boundary anchor. Click the combined map to choose your own point and automatically refresh the evidence. Distances remain recorded geometry distances, not routed travel times or entrance distances.

The map shows all applied service layers by default, with individual visibility toggles and category colours. Shared feature IDs appear once, retaining their criterion memberships. Local KPI counts refer to distinct records in loaded pages, not nationwide totals or estimated suitability. Each service initially loads up to 100 records. The record inspector can load subsequent spatial pages onto the map using the backend cursor and original query parameters. Points, lines, polygons and the geographic search radius are visible; “Fit visible records” adjusts the viewport without changing the anchor. Opening a feature popup does not move the anchor.

Monthly costs use entered household amounts and per-selected-service recurring expenses. Rental costs use the entered rent; purchase costs use constant-rate monthly mortgage amortisation from price, deposit, annual rate and term. Blank, negative and invalid amounts remain unknown. A subtotal is shown before all costs are entered; budget headroom is calculated only after all cost fields (including explicit zero service costs) and a monthly household budget are supplied. Household housing-budget preferences are separate from the total monthly budget. Upfront deposit and purchase fees are excluded from monthly totals. Costs survive service-priority edits and reset on a different place or tenure. Mixed transport remains a household preference and is omitted from mode-specific API parameters. Childcare parameters use a recorded child age rather than the first adult age. API requests retain the established 30-second timeout. Service prices are not inferred from map records.

Market-region selection uses `/market-geographies` and explicitly chosen publisher codes with `/market-context`; the UI does not infer a town crosswalk. Up to eight reported observations from the latest publisher period are shown with geography, property type, bedroom class and source provenance. These are unfiltered bedroom context and are never displayed as home listings. “Use as housing assumption” explicitly copies one observation into the housing calculator and labels its provenance; editing the amount clears that provenance. Explicitly saved household defaults persist in local storage. Current service choices and cost assumptions remain in memory during the visit. The backend receives selected criteria and relevant requested parameters and does not save them. Scores, eligibility, available properties and utility connection status remain unknown.

Map tiles come from the standard OpenStreetMap tile endpoint for ordinary interactive use; visible attribution is retained. Offline source layers continue to load even if external base tiles are unavailable. The live map shows source points, lines and polygons; it does not draw fabricated heatmaps or routes.

## Native macOS container demo

From the repository root, start the database and API, then run `bun run containers:frontend`. Open **http://127.0.0.1:5173**. The multi-stage image builds production React assets and serves them with Bun, proxying `/api` to the private API container. No Vite process is required. Recreate the frontend after recreating the API; its startup script discovers the current API address. The three host ports remain loopback-only.
